UPBGE 逻辑系统重构：整体架构与实施框架
一、设计原则

在动手前，先确立四条不可妥协的原则，它们决定了后续所有取舍：

    运行时零 Python 依赖——编辑器可以留在 Python，但游戏循环中的逻辑执行必须是纯 C++，通过偏移量直接访问扁平内存，彻底消除字典查找与解释开销。

    定义与运行时分离——节点的“结构定义”（引脚、UI、元数据）与“执行实例”（内存布局、执行逻辑）是两个独立类，编辑器改动不影响执行器，执行器重写不破坏编辑器。

    数据与行为分离——属性不再扁平绑定在对象上，而是封装为可共享、可复用的“数据资产”，逻辑节点和属性执行器都通过引用访问它。

    编译期确定一切——端口偏移、类型、连接拓扑、缓存指针槽位，全部在“Compile”阶段确定并固化，运行时只做最少的指针解引用与整数比较。

数据流方向：L4 编辑 → L3 编译 → L2 执行 → L1 读写。L4 的所有改动只在“Compile”时向下传递，游戏运行时 L3/L4 不参与逻辑执行。
三、核心子系统设计
3.1 执行引擎（L2）—— 编译式偏移链接模型

RuntimeData 缓冲区：每棵逻辑树在编译时分配一块连续内存，所有节点的输入/输出/状态都在其中占固定偏移。节点之间不传数据包，而是输入端口存储它连接的那个输出端口的偏移量，执行时直接按偏移读写同一块内存。
cpp

struct KX_RuntimeData {
    uint8_t* buffer;          // 扁平内存块
    size_t   size;
    // 编译期生成的访问表：port_id -> offset
};

节点运行时实例只保留执行必需的最小数据：
cpp

class KX_LogicNodeRuntime {
public:
    uint32_t input_offsets[MAX_INPUTS];   // 指向 RuntimeData 内偏移
    uint32_t output_offsets[MAX_OUTPUTS];
    uint32_t state_offset;                // Delay 等有状态节点的私有内存
    virtual ExecResult Execute(KX_ExecutionContext& ctx) = 0;
};

事件驱动调度：不再每帧遍历全图。触发套接字（Trigger）形成一棵以事件源为根的传播树，调度器从根出发沿触发边推进，只有被激活的节点才执行。值套接字（Value）则在节点执行时按偏移即时读取。

代际计数器缓存：访问 KX_GameObject 属性时，缓存“直接指针 + 代际号”。热路径仅需一次指针解引用和一次整数比较（~2-3 CPU 周期）；仅当属性映射变动（对象重建、组件替换）时代际号失配，才回退到字符串查找并刷新缓存。
3.2 数据资产系统（L1）—— 属性爆炸的解药

GameDataAsset 是一个引用计数的 C++ 对象，内部是一块带类型描述的紧凑内存：
cpp

class KX_GameDataAsset {
    std::vector<FieldDesc> fields;   // name, type, offset, default
    uint8_t* data;                   // 紧凑字段存储
    uint32_t refcount;
};

场景对象不再各自持有 health、speed，而是持有一个 AssetRef。多个对象引用同一资产时共享同一块内存，修改即全局生效。

引用属性：属性系统中的一种特殊类型，不持有值，而持有“目标资产 + 字段偏移”的解析结果。属性执行器与逻辑节点读取引用属性时，走与普通属性完全相同的偏移访问路径，但目标地址在编译期解析。

编辑器表现：资产在 Blender 的 Asset Browser 中创建和编辑，场景对象通过“挂载资产”建立引用。资产本身可以嵌套引用其他资产，形成配置层级。
3.3 编译与注册层（L3）—— 编辑器与运行时的桥梁

节点类型注册表：一张双向映射表，编辑器侧 bpy.types.Node 的类型标识 ↔ 运行时 KX_LogicNodeRuntime 的工厂函数。新增节点只需在 C++ 注册一个运行时类，并在 Python 侧注册对应的 UI 定义，两端通过字符串 ID 对齐。

图编译器：在“Compile”时执行——

    从节点树提取节点与连接；

    拓扑排序，检测环（允许经 Delay 节点形成的合法回边）；

    类型检查与隐式转换插入；

    为每个端口分配 RuntimeData 偏移；

    解析引用属性目标，填入缓存指针槽位；

    生成运行时节点实例数组与调度表；

    序列化为可热加载的二进制块（或直接生成 C++ 源码做 JIT）。

热重载：编译产物封装为独立模块（动态库或可替换的内存块），修改节点图后仅重新编译该模块并就地替换，游戏进程不重启。
3.4 编辑器体验层（L4）—— 补齐可用性短板

    节点分组（Group）：一组节点可折叠为单个执行单元，对外只暴露边界端口。编译期组内部仍走偏移链接，组作为整体参与外层调度，既提效又改善组织。

    数据检查器（Data Inspector）：独立于对象属性面板的全局窗口，按“数据资产/命名空间前缀”聚合展示属性，支持运行时实时编辑、引用关系反查（选中资产列出所有引用者）。

    调试可视化：执行引擎为每条触发边/值边维护轻量 visited 标记，编辑器经调试协议读取，实时高亮执行路径与被读取端口；支持在节点上设置断点、查看当前值。

    连线与导航改进：拖动连线时可缩放/滚动画布；长名称下拉菜单完整显示；对象选择器专用于调试挂载关系。

四、实施路线图（渐进式，每阶段可独立验证）
阶段	目标	关键交付物	验证标准
P0 地基	建立最小 C++ 运行时骨架	KX_RuntimeData、KX_LogicNodeRuntime 基类、KX_ExecutionContext、节点注册表	能在 C++ 中手工构造 3 节点图并正确执行
P1 最小执行器	5-10 个核心节点下沉	Float Math、Vector、Branch、Delay、Raycast 的运行时类 + 图编译器（排序/偏移分配）	与现有 Python 节点树输出一致，性能基准对比
P2 数据资产	属性爆炸解决方案 MVP	KX_GameDataAsset（Float/Int/Bool 字段）、对象挂载资产、逻辑节点“读取资产字段”	一个角色配置资产被多对象共享，修改即时生效
P3 编辑器闭环	编辑器可用性大幅提升	节点分组折叠、数据检查器面板、连线导航修复	复杂逻辑树（50+ 节点）编辑效率主观对比
P4 调试与热重载	可观测性与迭代效率	执行流高亮、断点、热重载模块加载器	修改节点图无需重启即可看到新行为
P5 全量迁移与 JIT	性能终极目标	全部内置节点 C++ 化、可选 C++ 代码生成 JIT 路径	逻辑执行性能接近手写 C++，对标 Godot Orchestrator

P0→P1 是风险最高的跳跃，建议用“双轨并存”策略：新 C++ 执行器通过编译标记启用，旧 Python 路径保留作为回退，直到 P2 稳定后再移除。
五、关键接口契约

为保证各层解耦，需提前锁定几个接口：

    L4→L3：CompileGraph(node_tree) -> CompiledModule，输入是 Blender 节点树，输出是运行时二进制块 + 元数据（调试符号、分组信息）。

    L3→L2：LoadModule(CompiledModule) -> ExecutionPlan，运行时按 ExecutionPlan 构造节点实例数组与调度表。

    L2→L1：ReadPort(offset) -> Value / WritePort(offset, Value)，节点执行只通过偏移访问 RuntimeData，不直接触碰属性系统；属性访问经 PropertyAccessor 统一封装，内置代际缓存。

    L1→L0：ResolveProperty(object, name) -> CachedPtr，唯一允许字符串查找的地方，结果被代际缓存保护。

六、总结

这套框架的核心思想可以浓缩为一句话：把“节点图”当作一门要编译的语言，而不是一堆要解释的对象。 编辑器负责表达意图，编译器负责把意图翻译成带偏移链接的扁平执行结构，运行时只做最少的指针运算，数据则以可共享资产的形式与行为彻底分离。按 P0 到 P5 的节奏推进，每个阶段都有可验证的产物，既能逐步兑现性能与体验的提升，也保留了随时回退到现有 Python 路径的安全网。
