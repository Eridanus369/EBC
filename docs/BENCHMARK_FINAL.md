## 1. 口径对齐（关键，先读）

A.4 的三条路径与 D.3 脚本的三条路径**不是一一对应**，映射如下：

| A.4 路径 | D.3 路径 | 能否配对 | 说明 |
|---|---|---|---|
| `native`（内联开启，默认） | `inline-on` | **可以** | 同一个 `KX_InlinePass` 折叠路径；A.4 折叠 98 节点，D.3 折叠 102 节点 |
| `BGE_GAMENODE_INLINE=off` | `inline-off` | **可以** | 同一非折叠路径 |
| 纯 Python 等价图（`8,458.1`） | — | **无对应** | 新脚本没有 Python 路径，本轮不重测、不对比 |
| — | `direct-call` | **不可比** | 它是 harness 内 `ApplyOp()` 直调链，**没有** `KX_GraphInstance`/plan/scheduler/节点对象，仅作 control |
| — | 引擎外渲染/物理 | 都无 | 两条基线都是「图执行微基准」，不含渲染/物理 |

三项口径差异（都已量化，不是猜测）：

1. **执行节点数不同**：A.4 图 = 1 OnUpdate + 2 ConstFloat + 96 FloatMath + 1 Sink，内联块 98 节点；脚本图 = 1 OnUpdate + 2 ConstFloat + **100** FloatMath + 1 Sink，`executed_nodes_per_frame=102`。所以帧级数字必须按 `ns_per_node` 复核。
2. **测量轮数不同（协议）**：A.4 **基线** = 3 个进程 × 内部 21 轮；A.4 **重跑**与 D.3 **最终值** = **5 个进程 × 内部 21 轮**（同协议）。因此 §0 的主配对用 A.4 重跑；A.4 基线（3×21）**仅作参考**。
3. **编译口径不同**：A.4 链接 clean 构建的 `libge_logic_bricks.a`，其编译参数含 `-O3 -DNDEBUG -fPIC -march=x86-64-v2 -fno-strict-aliasing -ffp-contract=off`；`run_benchmark.sh` 用 `harness_config.sh` **现编译** GameNodes TU，默认 `-O1` 且**没有 `-fPIC`**。这一条会显著改变绝对值（见 §2.3），因此同时给出了 `-O3` 与 `-O3 -fPIC` 两个对齐/诊断口径。

### 2.2 与 A.4 的配对对比

**双峰限定（先读）**：本机同一二进制、同协议换时窗会整体漂移 **1.54×**（快段 `310.142–320.772` µs、慢段 `446.208–485.972` µs，`frames=1000 × rounds=20 × best(min)`，证据 `/tmp/c4_perf_recheck.log`），且**不是负载造成的**（`loadavg=3.67` 时仍 10/10 在快段），也**不是 `taskset` 能消除的**（绑单核反而稳定在 `552` µs）。因此本节的判读分工是：

- **有效**：**同一时窗内的成对测量**——§2.1 的 `+1.34%` 是同一时窗内 5+5 进程的成对结果（跨进程、同窗），本报告可用的最严判据就是这一层；真正「同一进程内」的比值见 `b661_perf_v.cpp` 的 `ratio_*`（同进程测三张图）。
- **不可复现**：任何**跨运行**百分比，包括 §0 的 `+0.5% / +0.2%`、`−1.5% / +3.7%`，以及下面的 `+4.2% / −1.3%` 参考配对。它们只说明「那两次时窗里发生了什么」，不能作为门禁。
- **精度口径（按 harness 分开）**：本节数字来自 `a4_bench` / `d1_benchmark`（**median**），它们的重复精度分别 **约 5%** 与 **约 6–7%**；`b661_perf` 的 `±1%`（best-of）**不能给这里的数背书**。因此小于 5% 的差异一律只说「在精度内」，不写「更快/更慢」。
- 推论：A.4 的两次基线（`−3.9%` 原件 / `−4.1%` 新基线，均为慢段）与重跑（`+1.1%`）之间的**方向不一致**，**可能混有时窗双峰**，不全是内联效应本身的变化（各批的峰位未逐批记录，无法拆分）；叠加后符号不稳定，只能判「**量不到稳定收益**」。

| 配对 | A.4 | D.3 | 变化 | 协议 |
|---|---:|---:|---:|---|
| **同协议**：`inline-off` vs A.4 重跑 `inline_off` | 2606.9 | 2619.2 | **+0.5%** | 5 进程 × 21 轮 / 5 进程 × 21 轮 |
| **同协议**：`inline-on` vs A.4 重跑 `native` | 2577.9 | 2584.0 | **+0.2%** | 同上 |
| 参考：`inline-off` vs A.4 基线 `inline_off` | 2514.7 | 2619.2 | +4.2% | 3×21 / 5×21（**略异**） |
| 参考：`inline-on` vs A.4 基线 `native` | 2618.3 | 2584.0 | −1.3% | 同上 |
| 同上，按执行节点归一化 | 26.72 / 25.66 ns/node | 25.33 / 25.68 ns/node | **−5.2% / +0.1%** | — |

结论：同协议配对 `+0.5% / +0.2%`、跨协议参考配对 `+4.2% / −1.3%`，**全部小于 `a4_bench` 自身的跨运行重复精度（约 5%）**（其中 `+4.2%` 是唯一接近该精度的值）。`+4.2%` 在按节点归一化后基本消失（`+0.1%`），说明它是节点数口径（102 vs 98）造成的。**判定：未观测到超出测量精度的退化；不写「性能更好/更差」，也不把 ±5% 当门禁（`tests/` 中并无该门禁，见 §0）。**

**方向翻转（比单点值更重要）**

A.4 基线（21:08，**3 进程 × 21 轮**）测得开启内联**慢 3.9%**（native 2624.4 vs inline-off 2525.2；该次日志已于 23:39 被覆盖，不可复核）；**23:58 的新基线**（同一二进制、同一 `build_id`、**慢段**）再次给出**慢 4.1%**（2618.3 vs 2514.7）；本次 21:45 用同一被测二进制、同一台机器、同一 100 节点 Math 图重跑（**5 进程 × 21 轮**），得到开启内联**快 1.1%**（2577.9 vs 2606.9）。

因此现状是：**两个同向点（−3.9% / −4.1%）与一个反向点（+1.1%），符号不稳定**；`−4.1%` 不是「翻转」，也不能掩盖 `+1.1%`。

（严格说三次的进程数不同，且 `a4_bench` 的跨运行重复精度约 5%（本节顶部）：`−3.9% / −4.1%` 到 `+1.1%` 的跨度约 5.2 个百分点，正好贴着精度边界，因此只能记为「**方向不稳定**」。重跑的 5 个 native 进程有 4 个低于 2609，D.3 口径 A 也给出 `+1.34% 更快`，方向一致——这支持「不稳定」，不支持「翻转已确证」。）

下表约定：**收益 = (inline-off − inline-on) / inline-off；正 = 开启内联更快，负 = 更慢。**

| 测量来源 | 收益 | 方向 | 结论 |
|---|---:|---|---|
| A.4 基线（21:08，`build_clean_verify`，**3×21**） | −3.9% | 更慢 | 日志已丢失，不可复核 |
| A.4 **新基线**（23:58，同一二进制，`3×21`，慢段） | **−4.1%** | 更慢 | **第二个同向点；待查项**（见 `BENCHMARK_BASELINE.md` §0） |
| A.4 重跑（21:45，同一二进制，**5×21**） | +1.1% | 更快 | 唯一反向点 |
| D.1 `b662_jit`（`build_clean_verify`，harness 自有协议） | +1.42% | 更快 | 噪声内 |
| 另一线 `tests/run_benchmark.sh`（其自报） | +0.3% | 更快 | 噪声内 |
| JIT 线自测（其自有集合） | −0.40% | 更慢 | 噪声内 |

（A.4 的三行是**同一来源的三个测量区间**，因此独立来源共 **4 组**：A.4 / `b662_jit` / benchmark / JIT 线。）

由此得到三条结论：

1. **内联的真实效应落在各 harness 的重复精度内**：跨三次测量区间是 **−4.1% … +1.1%**（A.4 基线 3×21、新基线 3×21、重跑 5×21；同协议的 D.3 口径 A 为 +1.34%），**符号不稳定**；不能用其中任何一次的单点值当结论。**该区间混入了跨时窗双峰（本节顶部），只能当上界**；同一次测量会话内的成对值只有 `+1.34%`（D.3，5+5 进程同窗）与 `−4.1%`（A.4 新基线，3+3 进程同一次会话，慢段）两条。
2. **「JIT 只做图内联、收益约 3–4%」必须降级**：正确的说法是「**在 100 节点纯值图上量不到稳定收益**」。约 **3.5%** 只是 `build_linux` 上 **100 个 `ConstFloat` 最轻图**的正向上界（3.49%），不是普遍收益，更不能当作 JIT 的收益承诺。
3. **四组独立测量全部落在各自 harness 的重复精度内且方向不一致**（−4.1% / −3.9% / +1.1% / +1.42% / +0.3% / −0.40%；`a4_bench` 精度约 5%、`d1_benchmark` 约 6–7%）——这是「**40% 阈值不可达**」最有力的论证，比任何一次 −4.1% 的单点都强。

本报告**不为了统一口径而挑「代表值」**：这些测量互相矛盾，**不一致本身就是结论**。

### 2.3 口径 B / C：为什么 `-O3` 单独跑会「快 16–20%」（诊断，不是优化成果）

（协议同 §2：**5 进程 × 21 轮**，口径仅改变 `HARNESS_OPT`）

**双峰限定**：本表两行与 A.4 的对比是**跨运行**绝对数，`−15.4% / −20.2%` 与 `+5.4% / −0.9%` 均**不可复现**，只能读作量级。下面 `-fPIC` 的 `+24.2%` 同样是跨运行差值：方向可静态核对（clean 库确实带 `-fPIC`），但幅度会被时窗放大或缩小，**只能给量级，不能当精确系数**。

| 口径 | `inline-off` | `inline-on` | 相对 A.4 基线（3×21，仅参考） |
|---|---:|---:|---|
| B `-O3`，无 `-fPIC` | 2127.4 | 2089.6 | −15.4% / −20.2% |
| C `-O3 -fPIC` | 2649.8 | 2594.7 | +5.4% / −0.9% |
| A.4（库参数，3×21，新基线，慢段） | 2514.7 | 2618.3 | — |

- **`-fPIC` 是唯一已证实的差异来源**：同一份代码、同一图、同一台机器，仅加上 `-fPIC` 就从 **2089.6 → 2594.7 ns/frame**（+24.2%）。clean 构建的 `FLAGS` 中确实含 `-fPIC`（见 `build_clean_verify/build.ninja` 的 `FLAGS = ... -fPIC ... -O3 -DNDEBUG`），而 harness 默认不带。
- 因此**口径 B 的「快 16–20%」不是代码变快，是 harness 少了 `-fPIC`**，不能作为 D.3 成果对外引用。口径 C 与 A.4 参数一致后，差值回落到 +5.4% / −0.9%。
- 其余候选差异（unity build、链接 113 vs 46 个对象）已排除或无法解释：`libge_logic_bricks.a` 的 113 个成员是独立 `.cpp.o`（`ar t` 可见 `SCA_2DFilterActuator.cpp.o` 等），并非 unity 聚合；且先验影响远小于 20%。

### 2.4 并发环境记录（含实测负载）

A.4 重跑的每次运行前后都写了 `/proc/loadavg`，全部记录在
`/tmp/a4_bench_rerun_20261105-214556.log`：

| 时点 | loadavg（1/5/15 min） |
|---|---|
| 首轮之前 | `2.38 2.29 2.63` |
| native 前 4 次 | `2.38 → 2.46` |
| inline_off 前 5 次 | `2.38 2.29 2.63` → `2.50 2.32 2.63` |
| 全部结束 | `2.50 2.32 2.63` |

- 实测负载全程在 **2.3–2.6**（16 核机器），**并非** 1 分钟均值意义上的重负载；此前文中写的「1.88 → 3.51」**没有采集产物，已删除**。
- 但负载低 ≠ 无干扰：`inline_off` 第 2 个进程的 21 轮中位数是 **3669.2 ns/帧**，比同组其余四个进程（2553.4 / 2583.9 / 2606.9 / 2608.4）高约 **41%**，且 `min_ns_per_frame=3526.2` 整体抬升——这是典型的外部 CPU 争用（另一条线的构建/ASan/python）落在该进程的运行窗口内，而不是图执行本身变慢。该值在 5 进程里是唯一离群，中位数（2606.9）未被它带偏。
- 局限：`/proc/loadavg` 在本环境里更新很慢（整段约 1 分钟的运行期间只从 `2.38` 变到 `2.50`），**不能当作瞬时干扰指标**；判断干扰用的是「同一二进制多次运行的离群幅度」。
- 应对：A.4 与 D.3 最终值统一为 **5 个独立进程 × 每进程 21 轮中位数**，以抵抗单个离群进程。D.3 口径 A 的 5 个进程同样出现 2546.9–2729.9（`inline-off`）、2538.7–2695.9（`inline-on`）的离散（约 ±4%），与这里的 3669.2 同源，都是并发争用而非图执行差异。
- **未做**：没有为了拿低数字去停别人的进程或改 CPU governor。

## 3. JIT 40% 目标的最终数据

**本节是跨来源汇总，只作量级对照**：每一行是各自时窗/各自集合内的比值，**行与行不可比**；其中 A.4 两次基线 `−3.93% / −4.1%` 与重跑 `+1.1%` 的方向不一致同时受时窗双峰影响（§2.2 顶部），不是内联效应的稳定变化。

同一个「内联开关」在八组测量条目里的结果（约定同 §2.2：**正 = 开启内联更快**，收益 =(off−on)/off；D.3 各口径均为 **5 进程 × 21 轮**）：

| 来源 | 构建 / 图 | 内联收益 |
|---|---|---:|
| A.4 基线（21:08，3 进程 × 21 轮；日志已丢失） | `build_clean_verify` / 100 节点混合链（98 执行节点） | **−3.93%（更慢）** |
| A.4 **新基线**（23:58，3 进程 × 21 轮，慢段） | 同上 | **−4.1%（更慢）** |
| A.4 重跑（21:45，5 进程 × 21 轮） | 同上 | **+1.1%（更快）** |
| D.1 `b662_jit` | `build_clean_verify` / 25 rows × 400 ticks 混合负载 | **+1.42%（更快）** |
| D.3 口径 A（脚本默认，5 进程 × 21 轮） | `build_clean_verify` / 102 执行节点混合链 | **+1.34%（更快）** |
| D.3 口径 B（`-O3`，5 进程 × 21 轮） | 同上 | **+1.78%（更快）** |
| D.3 口径 C（`-O3 -fPIC`，5 进程 × 21 轮） | 同上 | **+2.08%（更快）** |
| JIT 线自测 | 其自有集合 | **−0.40%（更慢）** |

- 符号不一致、幅度全部在个位数（**−4.1% ~ +2.08%**），且**全部小于各自 harness 的重复精度**（`a4_bench` 约 5%、`d1_benchmark` 约 6–7%）→ **本集合内「内联收益」与测量精度不可区分**；A.4 的两次基线（`−3.93%` / `−4.1%`）与其重跑（`+1.1%`）方向相反（§2.2）。**`−4.1%` 不是「已确认的慢」，是待查项**（可能方向见 `BENCHMARK_BASELINE.md` §0）。
- 唯一有正向上界的实测是**最轻图**：`build_linux` 上 **100 个 `ConstFloat`** 图变快 **3.49%**。这只能表述为「**最轻图的上界约 3.5%**」，不能写成「开内联普遍快 3.5%」。
- **40% 目标实测不可达**：八组测量条目的收益都落在各 harness 自身重复精度之内（`a4_bench` 约 5%、`d1_benchmark` 约 6–7%）且方向不一致（见 §2.2 表），即便是最轻图的上界也只有 3.5%。要接近 40% 需要**直线特化（linear specialization）**，不是再加内联 pass。

## 4. 哪些改动可能影响性能（不归因）

本轮只测了三路径微基准，**没有做 A/B 归因实验**，以下仅为候选，不代表因果：

- **内联（`KX_InlinePass`）**：唯一有直接测量对象的项，结论见 §3。
- **Polar 布局 / 富文本解析 / UDP drain / zlib 压缩**：这些改动在引擎侧，**不在本微基准的执行路径内**（`KX_GraphInstance::Tick` 不经过布局、文本解析、网络或存档）。没有证据，故不归因。
- **构建口径**（`-fPIC`、`-O1 vs -O3`、链接对象集合）：已证明会带来 **±20%** 级别的绝对值差异，远大于任何候选代码改动的可能贡献；任何后续对比必须固定口径。

## 6. 局限

- 微基准只覆盖 `KX_GraphInstance::Tick` 的纯值链，不含渲染、物理、场景遍历、网络与 UI，不能外推为游戏帧率。
- 100 个随机 `FloatMath` 混合链（Add/Sub/Mul/Min/Max）仍不能代表含分支/trigger 的真实图；内联收益在分支图上可能不同。
- 机器非独占；本轮未隔离其他线，仅用多进程 + 中位数降低噪声。
- 脚本默认 `-O1` 是「harness 自身口径」，与产品二进制 `-O3 -fPIC` 不同；对外报数必须同时注明**编译口径**与**测量协议**（进程数 × 轮数 × 统计量）。
- 不同协议的绝对数之间**不存在可比性**：单进程单次（1×5×1）、本文最终值（5×21 中位）、A.4 基线（3×21 中位）三类只能在自己的协议内比较。
